# 验证记录：计划、发生与记录三个时刻

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

| 场景 | 结果 |
|---|---|
| 10-15 支付、10-16 改收货地址，用 `updatedAt` 当支付时间 | 支付时间显示为 2026-10-16T08:00:00Z；单独记录的 `paidAt` 是 2026-10-15T01:05:00Z |
| 纽约每天 9:00 提醒，第一次的 `Instant` 每天加 24 小时 | 10-30 是 9:00，夏令时结束后的 11-02 变成 8:00 |
| 存「09:00 + America/New_York」每次按当天计算 | 两天都是 9:00 |
| 三条读数按收到日期汇总 | 10-15 = 10，10-16 = 25 |
| 按发生日期汇总 | 10-15 = 30，10-16 = 5 |
| 补传的读数在 10-15 日报发出之后才到 | 需要一条更正记录 |
| 取消 01:59:58 提出、02:00:05 到达，任务 02:00:03 已执行；按收到时间 | 拒绝取消 |
| 按提出时间（早于计划时刻 02:00:00） | 应视为已取消，需要补偿 |
| 3 个计划任务，实际 − 计划 ≥ 5 分钟算迟到 | 2 个 |

## 五、误差、限制与不能推出的结论

- 这是对时间语义的演示，没有涉及调度框架、消息队列或数据库。
- 「用户提出的时间」来自客户端时钟，不可直接信任；实验只说明两个时间可能给出相反的结论，规则需要业务决定，并且服务端要有自己的记录时间。
- 时区规则来自 JDK 25.0.4.1 自带的 tzdata 版本，未来的规则变更会改变计算结果。

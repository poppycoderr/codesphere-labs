## 一、待验证结论与实际结果

| 场景 | 结果 |
|---|---|
| 在演算里生成咨询编号与取当前时间，同一条流重建两次 | 编号 C-1 与 C-2、开单时间相差 1 分钟，状态不相等 |
| 编号与时间在决定时写进事件 | 两次重建完全相等 |
| 评分 7、闭单后追加消息、重复关闭 | 都被拒绝，事件数不变 |
| 两个处理者都读到版本 2 | 先追加的成功（版本 3），后追加的因期望版本不符被拒；重新加载后按新状态被业务规则拒绝 |
| 摘要与回访写在一个处理器里，从头重建读模型 | 回访从 1 封变成 2 封 |
| 摘要投影与回访策略分开订阅，只重建摘要 | 摘要相同，回访仍是 1 封 |
| 同一条消息事件投递两次 | 无检查点时消息数 2，按全局位置跳过后为 1 |
| 6 个事件，在版本 4 做快照 | 快照加 2 个后续事件与完整重放相等 |

## 五、误差、限制与不能推出的结论

- 事件存储是内存实现，期望版本检查在单线程里顺序模拟两个处理者的交错，不涉及数据库的并发控制；真实存储要用唯一约束（流 ID + 版本）或条件写入实现同样的检查。
- 「在演算里生成编号」用计数器和每次前进一分钟的假时钟代替 UUID 与 Instant.now()，以便输出可比较；结论只依赖「每次调用得到新值」。
- 不涉及事件模式演进、快照与事件格式的版本兼容，以及隐私数据删除。

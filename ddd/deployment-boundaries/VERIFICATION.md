# 验证记录：从模型到部署单元

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

1. **边界在单体里也可以执行**：主代码 10 个类满足「报名模块只依赖通知 api」；违规夹具直接调用通知内部的模板方法，被规则拦下。
2. **规则有盲区**：另一个夹具只引用通知内部的 `static final String` 常量，违规 0 条。`javap` 显示字符串已被编译器内联进调用方，字节码里没有对那个方法或字段的访问，按字节码检查依赖的工具看不到它。
3. **业务规则不随部署方式变化**：同一组 3 个用例（确认与候补、重复报名、只通知已确认者）在同进程与 HTTP 两种部署下都通过。
4. **拆分引入的失败方式**（报名在提交前同步调用通知）：
   - 通知服务停止：20 次报名全部失败（`ConnectException`），已确认 0；
   - 通知处理耗时 800ms、客户端超时 300ms、最多 3 次：5 次报名全部回滚，客户端发出 15 次调用，通知服务在超时之后仍然处理完了，发出 15 条短信；每次报名约 900ms；
   - 通知服务按 noticeId 去重：短信降到 5 条，但 5 次报名仍然全部回滚，参会人收到了「已报名」的短信，报名却不存在。
5. **网络调用的额外延迟**：中位耗时同进程 11µs，本机 HTTP 487µs（各 500 次，前 100 次预热不计）。
6. **traceId 跨进程传递**：报名请求的 `trace-7f3a` 出现在通知服务的日志中。

## 二、环境

见 [`evidence/environment.txt`](evidence/environment.txt)。组件版本：jdk 21、archunit 1.5.0、junit 5.13.4。

## 三、执行步骤

`mvn test` 运行 3 个测试类、11 个用例，事实写入 `target/facts.tsv`；随后用 `javap -c` 截取常量夹具的字节码。超时用例在最后一次调用后等待 2.5 秒，让通知服务处理完已接收的请求再计数。

## 五、误差、限制与不能推出的结论

- 「拆分」只是把通知放到同一 JVM 里的另一个 HTTP 服务端，走本机回环网络；没有跨机器网络、服务发现、负载均衡与 TLS，真实环境的延迟和失败率更高。
- 延迟中位数取决于机器，断言只要求 HTTP 大于同进程。
- 报名用例故意在提交前同步调用通知；这组数字说明的是这种写法在拆分后的后果，不是推荐做法。
- 没有测试「通知服务部分可用」「慢但不超时」等更多组合。

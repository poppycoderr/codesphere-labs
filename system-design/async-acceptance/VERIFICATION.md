# 验证记录：受理不等于完成

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

JDK 25.0.4.1。

1. `POST` 返回 202、`Location: /jobs/job-1`、状态 `QUEUED`；后台执行完之后 `GET` 返回 `FAILED`（`source table missing`）。
2. 服务端登记任务后 600 毫秒才响应，客户端 200 毫秒超时。不带幂等键重试：返回 `job-2`，服务端登记了 2 个任务。带同一个 `Idempotency-Key` 重试：返回 `job-1`，服务端只有 1 个任务。
3. 任务还在排队时查询到 `QUEUED`：「不是 RUNNING 就算结束」判断为 true，「属于终态集合才算结束」判断为 false。
4. 任务表在内存里：重启后 `GET job-1` 返回 404。任务表持久化、没有租约：重启并经过 100 个时间单位后仍是 `RUNNING`，后台再取任务得到 null。带租约：重启后任务回到 `QUEUED`，被重新取出并执行成功。
5. 任务成功后到达迟到的进度上报：无条件写入时状态变回 `RUNNING`；只允许向前时写入被拒绝，重复的完成上报也被拒绝，状态保持 `SUCCEEDED`。
6. 租约过期后任务被第二个执行者接手（attempt 2）。旧执行者上报完成：只检查状态时写入成功，任务被记为 `SUCCEEDED`；检查执行序号时旧执行者（attempt 1）的上报被拒绝，当前执行者的上报被接受。

## 五、误差、限制与不能推出的结论

- 「持久化」在实验里是重启前后复用同一个对象，没有真实的数据库；持久化本身的原子性（登记任务与写幂等键要在同一个事务里）没有验证。
- 时间与租约用逻辑时钟推进，没有真实的心跳、时钟漂移与网络分区。
- 任务重新排队意味着会执行第二次，任务本身是否幂等不在实验范围内。
- 没有覆盖取消、结果过期、回调通知、任务的权限检查与限流。

# 验证记录：未读数的两种存法

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

| 场景 | 计数器 | 已读位置 |
|---|---|---|
| 发了 10 条，其中 3 条的通知被重复投递 | 13 | 10 |
| 看完前 10 条后上报已读，请求到达前第 11 条已写入 | 清零后 0，实际有 1 条没看过 | 1 |
| 千人群发一条消息要更新的行数 | 999 | 0 |

已读位置这种存法自己的问题：

| 场景 | 结果 |
|---|---|
| 手机上报读到第 20 条，随后电脑上迟到的请求上报第 12 条，直接覆盖 | 未读从 0 变成 8 |
| 写成 `last_read_id = GREATEST(last_read_id, ?)` | 未读 0 |
| 发送者自己的 20 条消息，不排除 | 20；排除后 0 |
| 事务 A 先插入（ID 较小）未提交，事务 B 后插入先提交；读者把已读位置记到 B 的 ID，之后 A 提交 | 未读 0，但 A 的那条读者从没见过 |
| 一个事务插入后回滚 | 下一条消息的 ID 跳过了一个号 |
| 按会话 `SELECT … FOR UPDATE` 分配序号：A 未提交时 B 来取 | B 等待，1 秒后锁等待超时 |
| A 提交后 B 重试 | A 的序号 1，B 的序号 2 |
| 5000 条未读，只数到 100 就停 | 100（完整计数 5000） |

## 五、误差、限制与不能推出的结论

- 所有交错都是用两条连接手工排出来的，说明的是「这种顺序会导致这个结果」，不说明它在某个负载下出现的频率。
- 按会话加行锁分配序号把同一会话的写入串行化了，热点会话（大群）的写入吞吐会受这把锁限制，实验没有测量。
- 没有覆盖把计数或已读位置放在 Redis 里的做法；原子自增能避免并发丢失，但重复投递与清零交错的问题与存储无关。
- 封顶计数只演示了查询写法，没有在大表上比较两种写法的耗时。

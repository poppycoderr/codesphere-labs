# 验证记录：依赖任务图的执行

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

1. **发布前校验要分开报告四类错误**：同一份配置报出「重复节点: 通知准备」「缺失节点: 提交 依赖的 发票 不存在」「循环依赖: 名额预留 -> 资格校验 -> 名额预留」「受环阻塞: [提交, 费用计算]」。箭头表示「依赖」。Kahn 算法剩下的 4 个节点里只有 2 个在环上。
2. **普通队列的顺序随声明顺序变化**：同一张图倒序声明后，三个并行分支的顺序从「费用计算、通知准备、风控复核」变成「风控复核、通知准备、费用计算」；ready 集合按名称排序后，两种声明给出相同顺序。
3. **并发上限决定总耗时，关键路径是下限**：各节点耗时之和 850ms，关键路径 450ms。上限 1、2、3 的总耗时为 881ms、678ms、471ms，同时运行的节点数分别等于上限。
4. **失败传播由策略决定**：费用计算失败后：
   - 跳过后继：通知准备、风控复核照常成功，只有提交被跳过；
   - 立即取消：运行中的通知准备、风控复核被取消，提交被跳过。
5. **重试需要幂等键**：名额预留第一次调用已经扣减名额但响应超时，重试一次。不带幂等键占用 2 个名额；带「run_id + 节点」作为幂等键时只占用 1 个。

## 二、环境

见 [`evidence/environment.txt`](evidence/environment.txt)。JDK 21.0.5。

## 三、执行步骤

`java src/DagRunner.java`。节点用 `Thread.sleep` 模拟耗时（100ms、200ms、50ms）；调度器用固定大小的线程池和 `ExecutorCompletionService`，节点完成后才把入度归零的后继放进 ready 集合。

## 五、误差、限制与不能推出的结论

- 耗时来自 `Thread.sleep`，只断言与关键路径和并发上限的关系：上限 1 不少于 850ms，上限 2 在 650—800ms，上限 3 在 450—600ms。
- 取消依赖任务响应中断。真实任务如果不检查中断（例如阻塞在不可中断的 I/O 上），「立即取消」只能停止调度新节点。
- 重试在节点内部模拟，幂等键由被调用的服务去重；没有模拟调度器进程崩溃后的恢复。

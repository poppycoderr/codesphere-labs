## 一、待验证结论与实际结果

| 场景 | 结果 |
|---|---|
| 开票与退款各写一遍 6% 税率 | 都是 106.00 |
| 税率改成 9%，只改到开票 | 开票 109.00，退款 106.00 |
| 两处都调用同一个税率来源 | 都是 109.00 |
| 昵称与优惠码规则一样时，优惠码「七折优惠」 | false |
| 合并规则后按昵称的新需求（支持中文）修改 | 优惠码「七折优惠」也变成 true |
| 原写法：写入失败、通知也失败 | 调用方收到写入失败 |
| 提取成公共方法（少了内层 try） | 调用方收到通知服务不可用 |
| 提取时把通知失败挂到原异常上 | 收到写入失败，suppressed 里有通知失败 |
| 日志关闭时循环 1000 次，昂贵的消息构造 | 内联 0 次；提取成普通参数 1000 次；改成 Supplier 0 次 |
| `cheapCheck() && consumeQuota()` 100 次 | 额度扣 0 次；提取成 `both(a, b)` 后扣 100 次 |

## 五、误差、限制与不能推出的结论

- 都是构造出来的最小例子，说明的是「提取会改变哪些语义」，不代表某个真实系统里出现的频率。
- 没有覆盖提取后改变的同步范围、事务边界与异常类型（受检异常的声明），它们是同一类问题。

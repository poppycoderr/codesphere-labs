# 验证记录：并行流与公共线程池

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

主实验（JDK 25.0.4.1，并行度 3，每次阻塞 200 ms）：

| 场景 | 结果 |
|---|---|
| 一个请求，8 次阻塞调用放进并行流 | 公共池线程与调用线程一起执行，417 ms（两轮） |
| 一个请求，4 次阻塞调用 | 208 ms |
| 8 个这样的请求同时进来 | 407、409、614、616、617、828、829、829 ms；最慢的等于 4 次调用完全串行 |
| 12 个阻塞任务，`runAsync` 不传执行器 | 运行在公共池线程，831 ms（四轮） |
| 这期间提交的一个空任务 | 等了 829 ms 才开始执行 |
| 这期间的一个纯计算并行流 | 只有调用线程参与，4 ms |
| 同样 12 个任务交给 12 线程的专用线程池 | 208 ms |
| 在 `new ForkJoinPool(8)` 里提交 8 次阻塞调用的并行流 | 只有自建池的线程参与，212 ms |
| 调用线程设置 `ThreadLocal` 后跑并行流 | 调用线程读到值，公共池线程读到 null |
| 并行流里 `forEach(list::add)` 往 `ArrayList` 放 10 万个元素 | 丢元素、出现 null 或抛异常；`collect(toList())` 得到 100000 个 |
| 静态初始化块里跑并行流，lambda 调用本类的静态方法 | 5 秒内没有结束 |

不同 CPU 数下公共池的大小（JDK 25）：1 个与 2 个 CPU 时并行度都是 1，4 个时是 3，8 个时是 7。

不带执行器的 `supplyAsync`，6 个 200 ms 的阻塞任务：

| JDK | 1 或 2 个 CPU | 4 个 CPU |
|---|---|---|
| 8u504 | 每个任务新建一个线程，约 1 轮（210 ms） | 公共池，约 2 轮 |
| 21.0.12 | 每个任务新建一个线程，约 1 轮（212 ms） | 公共池，约 2 轮 |
| 25.0.4.1 | 公共池，约 6 轮（1252 ms） | 公共池，约 2 轮 |

## 五、误差、限制与不能推出的结论

- 耗时是单次运行的结果，只用来判断落在哪个区间；`sleep` 代替的阻塞调用不占 CPU，真实的阻塞调用还会受下游影响。
- 8 个请求同时进来时各自的耗时取决于公共池线程先帮了谁，分布每次不同，脚本只断言「超过 550 ms 的不少于 4 个，最慢的在 750—1100 ms」。
- 「在自建的 ForkJoinPool 里提交并行流就用那个池」是当前实现的行为，`Stream` 的文档没有承诺。
- 公共池并行度可以用 `-Djava.util.concurrent.ForkJoinPool.common.parallelism` 指定，实验用的是由 CPU 数推出来的默认值。
- 没有覆盖虚拟线程；虚拟线程的调度器是另一个独立的池。

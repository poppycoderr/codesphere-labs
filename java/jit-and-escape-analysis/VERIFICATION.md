# 验证记录：JIT 与逃逸分析

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

同一个「`new Point(x, y)` 再计算距离平方」的方法，每次调用实际分配的字节数（最后 10 批的中位数，每批 20 万次调用）：

| 条件 | 第 1 批 | 稳定后 |
|---|---:|---:|
| 点只在方法内使用（默认参数） | 4.2 | 0 |
| 点传给另一个方法，且能被内联（默认参数） | 18.1 | 0 |
| 点传给接口方法，调用点见过 2 种实现（默认参数） | 2.6 | 0 |
| 点写进静态字段（默认参数） | 24.0 | 24 |
| 点传给接口方法，调用点见过 4 种实现（默认参数） | 24.0 | 24 |
| 点只在方法内使用，`-XX:-DoEscapeAnalysis` | 24.0 | 24 |
| 点传给另一个方法，`-XX:CompileCommand=dontinline` 禁止内联 | 24.0 | 24 |
| 点只在方法内使用，`-Xint` 只解释执行 | 24.0 | 24 |

结论：

1. 一个 `Point` 对象在这台机器上占 24 字节。JIT 编译后，不逃逸的对象被消除，每次调用分配 0 字节。
2. 消除分配依赖逃逸分析（关闭后恢复 24 字节）、依赖编译（只解释执行时 24 字节），也依赖内联：对象传给一个没被内联的方法，编译器就无法证明它不逃逸。
3. 调用点的多态程度会改变结果：见过 2 种实现时仍能内联并消除分配，见过 4 种实现后不再内联，每次分配 24 字节。
4. 第 1 批的平均值高于 0，是因为前面一部分调用还在解释执行或在低层级编译代码中运行。

## 二、环境

见 [`evidence/environment.txt`](evidence/environment.txt)。JDK 21.0.5（HotSpot，默认启用压缩类指针）。

## 五、误差、限制与不能推出的结论

- 这是 HotSpot C2 在当前版本和参数下的行为，不是 Java 语言规范的保证；Graal 等其他编译器的结果可能不同。
- 「2 种实现可以内联、4 种不行」对应 HotSpot 的双态内联策略；具体阈值与类型剖析数据有关，不同版本可能变化。
- 只测量了分配字节数，没有测量耗时。分配消除是否带来可见的性能收益，要在真实负载下用 JFR 或 JMH 验证。
- 对象大小 24 字节来自 12 字节对象头加两个 `int`，再按 8 字节对齐；关闭压缩指针等参数会改变它。

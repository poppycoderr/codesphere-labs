# 验证记录：公平锁的代价、条件队列与 tryLock 插队

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论

1. 8 个线程抢同一把锁：公平锁的吞吐只有非公平锁的百分之一左右，各线程获取次数几乎完全均匀
2. 可重入计数：加锁 3 次后 `getHoldCount()` 为 3；多释放一次抛 `IllegalMonitorStateException`
3. 3 个线程 `await` 后在条件队列；`signalAll` 之后、`unlock` 之前，它们在同步队列里，状态仍是 `WAITING`
4. 公平锁上，已有线程排队时 `tryLock()` 会插到排队线程前面；`tryLock(0, SECONDS)` 遵守公平策略，排队线程还在队列中时从不成功

## 五、误差、限制与不能推出的结论

- 吞吐绝对值随机器变化：文章中非公平锁约 4,696 万次/秒、公平锁约 46 万次/秒；本仓库归档的一次是 4,347 万、51 万（约 1/84）。本机连续几次运行中两者的比值在 1/70 到 1/120 之间，稳定的结论是「相差约两个数量级」。`synchronized` 在各线程之间的分配随 JDK 版本和环境变化（几次运行中最多/最少在 1.1—2.2 倍之间），文章已说明不应依赖。
- `tryLock` 实验最初只统计「成功次数」，在 GitHub Actions 的 4 核机器上出现 `tryLock()` 132/200、`tryLock(0, SECONDS)` 176/200 的反转：带超时的版本成功，是因为排队线程已经拿到锁、用完并释放，队列已空，这取决于调度快慢。现在改为统计**成功时排队线程是否仍在队列中**，也就是真正的插队：本机 `tryLock()` 约 190/200 次、`tryLock(0, SECONDS)` 0 次；限制为 2 核的容器中是 96 次与 0 次。插队次数随核数和调度变化，「带超时的版本在有人排队时从不成功」是由公平策略保证的。
- 限制为 2 核的容器中，8 个线程的公平锁吞吐降到约 7 万次/秒（非公平约 4,500 万次/秒），与文章「线程数超过核数时差距更大」一致。

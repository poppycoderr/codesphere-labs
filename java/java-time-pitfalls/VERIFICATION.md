# 验证记录：java.time 的边界

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

JDK 25.0.4.1，时区数据 2026b。

1. 时间点 `2026-10-09T02:00:00Z` 在上海是 10-09 10:00，在洛杉矶是 10-08 19:00。本地时间 `2026-10-09T10:00` 按上海与按纽约解释相差 12 小时。
2. 纽约 `2026-03-07T12:00` 加 1 天得到 03-08 12:00，实际经过 23 小时；加 24 小时得到 03-08 13:00。不存在的 `2026-03-08T02:30` 被解析为 03:30；出现两次的 `2026-11-01T01:30` 默认取 -04:00 的那一次，两次相差 60 分钟。纽约 2026-03-08 这一天共 23 小时。
3. `2026-01-31` 加 1 个月得 02-28，再加 1 个月得 03-28；直接加 2 个月得 03-31。`2026-01-31` 到 `2026-03-01`：`Period` 是 `P1M1D`，`getDays()` 为 1，`ChronoUnit.DAYS.between` 为 29。`30 * 24 * 60 * 60 * 1000` 用 `int` 计算得 -1702967296。
4. `2026-12-27` 用 `YYYY-MM-dd`（`Locale.US`）格式化得 `2027-12-27`；15:05 用 `hh:mm` 得 `03:05`；`2026-02-10` 用 `yyyy-MM-DD` 得 `2026-02-41`。
5. 默认解析 `2026-02-30` 得 `2026-02-28`，解析 `2026-02-32` 抛 `DateTimeParseException`。STRICT 加 `yyyy` 解析合法的 `2026-02-10` 也抛异常；STRICT 加 `uuuu` 解析 `2026-02-10` 成功、解析 `2026-02-30` 抛异常。
6. 同一时间点的上海与 UTC 两个 `ZonedDateTime`：`equals` 为 false，`isEqual` 为 true。`new Date(2026, 10, 9)` 表示 3926-11-09。

## 五、误差、限制与不能推出的结论

- 夏令时的日期取决于时区数据（本次为 2026b）。各地的规则会被立法修改，时区数据更新后同一段代码对未来日期的结果可能变化。
- `YYYY` 的结果取决于区域设置对「一年的第一周」的定义，这里用的是 `Locale.US`；换成 ISO 定义，出错的日期不同。
- 没有覆盖数据库驱动与列类型（`TIMESTAMP`、`DATETIME`）的时区转换、JSON 序列化的时间格式，以及闰秒。

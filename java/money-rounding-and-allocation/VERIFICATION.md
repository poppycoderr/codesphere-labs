# 验证记录：金额的舍入与分摊

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

把 2.675 保留两位：

| 写法 | 结果 |
|---|---|
| `new BigDecimal(2.675).setScale(2, HALF_UP)` | 2.67 |
| `new BigDecimal("2.675").setScale(2, HALF_UP)` | 2.68 |
| `Math.round(2.675 * 100) / 100.0` | 2.68（`Math.round(1.005 * 100) / 100.0` 是 1.0） |
| `String.format("%.2f", 2.675)` | 2.68 |
| `new DecimalFormat("0.00").format(2.675)` | 2.67（默认 `HALF_EVEN`） |

- `new BigDecimal(0.1)` 是 0.1000000000000000055511151231257827021181583404541015625；`new BigDecimal(2.675)` 是 2.67499999999999982236431605997495353221893310546875。
- `(long) (19.99 * 100)` 是 1998；0.00 到 99.99 一万个金额里这样转换出错的有 573 个。`new BigDecimal("19.99").movePointRight(2).longValueExact()` 是 1999。
- 1000 笔恰好落在半分上的金额（0.005 到 9.995）：精确合计 5000.000，逐笔 `HALF_UP` 合计 5005.00，逐笔 `HALF_EVEN` 合计 5000.00。
- `1 ÷ 3` 不指定精度抛 `ArithmeticException`，`1 ÷ 4` 不抛；`new BigDecimal("10").divide(new BigDecimal("3"), HALF_UP)` 是 3，被除数写成 `"10.00"` 是 3.33；`new MathContext(2)` 把 1234.567 变成 1.2E+3；`new BigDecimal("100.00").stripTrailingZeros()` 的 `toString` 是 `1E+2`。
- 3 件 0.99 的商品、税率 8.25%：逐行算税合计 0.24，按合计算税 0.25。

拆分：

| 做法 | 结果 |
|---|---|
| 100.00 平分 3 方，各自舍入 | 33.33 × 3 = 99.99 |
| 0.05 平分 10 方，各自 `HALF_UP` | 0.01 × 10 = 0.10 |
| 同上，最后一份拿余数 | 最后一份 -0.04 |
| 0.05 按 5:3:2，各自 `HALF_UP` | 0.03 + 0.02 + 0.01 = 0.06 |
| 最大余数法，100.00 按 1:1:1 | 33.34、33.33、33.33，合计 100.00 |
| 最大余数法，0.05 按十个 1 | 五个 0.01、五个 0.00，合计 0.05 |
| 最大余数法，0.05 按 5:3:2 | 0.03、0.01、0.01，合计 0.05 |

- 3 件 33.33 的商品用 10.00 的优惠、实付 89.99：退款时按比例现算每件 30.00，三件都退合计 90.00；下单时用最大余数法分好并保存是 30.00、30.00、29.99。
- `Currency.getDefaultFractionDigits()`：USD、CNY 为 2，JPY、KRW 为 0，KWD、BHD 为 3，CLF 为 4。

## 五、误差、限制与不能推出的结论

- `Math.round`、强制转换的结果取决于具体数值的二进制表示，573 这个数字只对「0.00 到 99.99、乘 100 后强制转换」成立。
- 最大余数法在余数相同时按原顺序分配，这是实验里的约定；实际业务要自己规定并写进规则（按金额大小、按固定顺序等）。
- 没有覆盖税法或会计准则规定的舍入规则，那些以适用的规定为准；也没有覆盖汇率换算。
- 货币小数位来自 JDK 自带的 ISO 4217 数据，随 JDK 版本更新。

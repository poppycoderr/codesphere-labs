# 验证记录：队列有界，不等于在途有界

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

JDK 25.0.4。

1. **批的上限**：队列积压 1000 条，`drainTo(batch)` 得到 1 批 1000 条；`drainTo(batch, 99)` 得到 10 批，最大 100 条。
2. **在途量**：队列容量 100，下游卡住 500ms。不限在途时，生产者放完 5000 条没有被阻塞，队列里 0 条，5000 条都已交给写入线程但未写完；在途额度 200 时，生产者放入 350 条后被阻塞（在途 200、队列 100、消费者手里一批 50）。
3. **按时间刷出**：每 80ms 到达一条。每次 `poll(100ms)` 重新计时，第一批攒到 10 条，第一条等了 864ms；按批的截止时间，第一批 2 条，第一条等了 102ms。
4. **批内失败**（批大小 50）：
   - 异常逃出循环：写入 0 条，已取出但没写入的好数据 49 条，留在队列里 50 条；消费者线程退出，生产者放满队列后被阻塞；
   - 捕获后只记日志：写入 50 条，同批的 49 条好数据丢失；
   - 逐条重试：写入 99 条，坏数据进死信 1 条。
5. **关闭**：消费者已取出 20 条尚未写入时中断。直接退出：写入 0 条，丢失 100 条；排空并写完：写入 100 条，丢失 0 条。
6. **毒丸**：队列已满时 `offer(毒丸)` 返回 false；2 个消费者只放 1 颗，仍有 1 个消费者在运行；补上第 2 颗后为 0 个。

## 五、误差、限制与不能推出的结论

- 第 2 点在途受限时生产者放入的条数取决于被阻塞时消费者手里的批大小，断言范围 300—350；第 3 点的毫秒数随调度波动，断言只检查「不少于 700ms」与「不超过 150ms」。
- 下游是内存模拟，没有涉及真实数据库的批量写入失败语义（部分成功、唯一键冲突等），那部分见 `storage/` 下的导入实验。
- 关闭场景假设上游已经停止放入；上游仍在写入时，排空没有终点，需要先停上游。
- 进程崩溃时内存队列里的数据必然丢失，本实验的「不丢」只针对正常关闭。

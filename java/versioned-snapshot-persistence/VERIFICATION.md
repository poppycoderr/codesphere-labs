# 验证记录：脏标记与版本化快照

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

JDK 25.0.4。

1. **先清脏标记再保存**：修改为 v1，第一次保存失败，之后又跑两轮：`dirty=false`，存储里仍是 v0，存储只被调用了 1 次。
2. **保存成功后清标记**：v1 保存期间修改为 v2，保存完成后 `dirty=false`，存储里是 v1，之后两轮没有触发保存。
3. **逐字段读取**：保存线程读完第一个字段后，另一线程把 30 从线上挪到线下；存储里是 `online=60 offline=70`，两项之和 130，内存里始终是 100。
4. **版本化快照**：第一次保存失败后已保存版本仍为 0，下一轮重试后为 1；第 2 版保存期间修改为第 3 版，保存完成时已保存版本 2、内存版本 3，下一轮后已保存版本 3。
5. **乱序写入**：第 5 版先写入、第 4 版后到。存储不比较版本时最终内容是第 4 版；按版本条件写入时两次分别返回 true、false，最终内容是第 5 版。

## 五、误差、限制与不能推出的结论

- 场景是用闩锁排出来的确定时序，说明这些写法存在问题，不说明它们在真实负载下出现的频率。
- 存储是内存模拟。真实存储里「按版本条件写入」对应带版本条件的 `UPDATE`、对象存储的条件写等，各自的原子性保证需要另行确认。
- 没有涉及进程崩溃：未保存的修改只在内存里，崩溃即丢失；写入是否落盘取决于存储自身。

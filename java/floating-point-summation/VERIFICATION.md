# 验证记录：浮点求和的顺序与精度

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

JDK 25.0.4。

1. `new BigDecimal(0.1)` 是 0.1000000000000000055511151231257827…；`0.1 + 0.2` 得 0.30000000000000004；0.1 累加 10 次得 0.9999999999999999。
2. `1e16` 附近相邻两个 double 相差 2：`1e16` 之后加 10 个 1.0 仍是 10000000000000000，先加 10 个 1.0 再加 `1e16` 得 10000000000000010。`(0.1+0.2)+0.3` 与 `0.1+(0.2+0.3)` 分别是 0.6000000000000001 与 0.6。
3. `float` 累加 2000 万个 1.0f 得 16777216（2^24）；累加 1000 万个 0.1f 得 1087937.0，`double` 得 999999.9998389754。
4. 1000 万笔金额（0.01—9999.99，固定种子），按分用 `long` 累加为 49996274454.21；这些 `double` 的精确和与它相差约 -1.1e-9。相对精确和的误差：逐个累加 +0.0024，Kahan、Neumaier 与顺序流的 `DoubleStream.sum()` 都是 -9.1e-7，两两归并 -8.5e-6，升序排序后逐个累加 +0.0015。分成 1、2、3、4、6、8、16 块各自累加再合并，得到 7 个互不相同的结果（误差 -0.0019 到 +0.0024）。逐个累加的和保留两位小数后与按分累加一致。用 `float` 逐个累加得 49472577536。
5. `[1, 1e100, 1, -1e100]`：逐个累加、Kahan 与 `DoubleStream.sum()` 得 0.0，Neumaier 得 2.0。
6. `long` 9007199254740993 转 `double` 再转回得 9007199254740992；3 个这样的值用 `double` 累加得 27021597764222976，用 `long` 得 27021597764222979。`new BigDecimal(0.1)` 与 `BigDecimal.valueOf(0.1)` 不相等；`new BigDecimal("1.10").equals(new BigDecimal("1.1"))` 为 false 而 `compareTo` 为 0。含 NaN 的数组求和得 NaN。

## 五、误差、限制与不能推出的结论

- 误差的具体数值取决于这组数据（固定种子生成）与累加顺序，换一组数据数值会变；能推出的是「顺序与分块方式会改变结果」和各方法误差的数量级关系，不是某个固定的误差值。
- 分块归约是在单线程里按固定块数模拟的。并行流的切分方式由运行时的并行度决定，没有在本实验中运行，因此不对并行流的具体结果下结论。
- 本次数据里逐个累加的和保留两位小数后仍与精确值一致，不代表数据量更大或金额更大时也一致。
- 没有覆盖 `strictfp` 之前的行为（JDK 17 起所有浮点运算都是严格的）、FMA 与向量化对结果的影响。

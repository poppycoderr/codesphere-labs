# 验证记录：LSM 树的放大

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

写入 180 MB 用户数据：

| 场景 | 刷盘写入 | 压实写入 | 写放大 |
|---|---|---|---|
| 顺序键，分层压实 | 179 MB | 0 MB | 1.0 |
| 随机键，分层压实 | 181 MB | 516 MB | 3.9 |
| 随机键，通用压实 | 181 MB | 482 MB | 3.7 |

| 场景 | 文件大小 |
|---|---|
| 30 万个键（36 MB）写 5 遍，未压实 | 179 MB |
| 压实之后 | 36 MB |
| 全部删除之后、压实之前 | 40 MB，读取已经读不到 |
| 再压实之后 | 0 MB |

脚本只断言范围：顺序键写放大约 1，随机键 2.5 以上，覆盖写压实前约 5 份、压实后约 1 份，删除后压实前文件不减，压实后归零。

## 五、误差、限制与不能推出的结论

- 写放大不含预写日志；算上它每个场景再加约 1。
- 数据量只有 180 MB、层数很少，写放大比生产规模的库小得多；这里只说明顺序与随机的差别和量级的来源。分层与通用压实在这个规模上差别不大，不能据此比较两种策略。
- 关闭了压缩。开启压缩后按磁盘字节计的放大会变小，CPU 开销增加。
- 没有测量读放大、压实对前台延迟的影响，也没有在真实的固态盘上测量寿命或稳态性能。
- 覆盖与删除两个场景关闭了自动压实，是为了看清「压实之前」的状态；默认配置下压实会在后台陆续进行。

# 验证记录：测试数据的归属

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

| 场景 | 结果 |
|---|---|
| 两个测试的准备步骤都插入 `test@example.com` | A 成功，B 唯一键冲突 |
| A 断言「NEW 状态的订单有 1 条」，B 也下了一单 | 实际 2 条，A 失败 |
| 断言改成只数自己那个用户的订单 | 1 条，A 通过 |
| B 的清理 `DELETE … WHERE email LIKE 'test%'` | 删了 2 行，A 查自己的用户 0 行，A 失败 |
| 数据带运行标识，清理只删自己的 | 删了 1 行，A 通过 |
| 上一次运行留下了固定邮箱，这一次再插入 | 唯一键冲突 |
| 邮箱里带本次运行的标识 | 成功；上次留下的行仍在 |
| 在不提交的事务里准备数据 | 同一条连接看到 1 行，另一条连接看到 0 行 |
| 事务未结束时另一个测试插入同一个邮箱 | 等锁 1 秒后超时 |
| 回滚之后再插入一行 | 自增 ID 是 3，表里只有 1 行 |
| 两个进程各用一个库，都用固定数据、数整张表、按模式清理 | 互不影响 |

## 五、误差、限制与不能推出的结论

- 交错顺序是手工排的，说明的是「这种顺序会出这个结果」。真实的并行测试里它表现为偶发失败，频率取决于测试数量与并行度，实验没有测量。
- 「每个进程一个库」只验证了数据互不影响，没有测量建库、建表、迁移的耗时。
- 只覆盖了数据库。消息队列的主题、缓存的键、对象存储的路径、外部沙箱账号有同样的归属问题，没有做实验。
- 没有覆盖测试框架提供的事务回滚机制的细节（例如哪些情况下被测代码会用到同一个事务），那取决于具体框架。

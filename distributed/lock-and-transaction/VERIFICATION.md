# 验证记录：锁与事务的边界、状态流转与主键类型

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

1. **锁必须包住事务**（200 个用户 × 20 个线程）：
   - 锁在提交前释放：223 条订单，22 个用户出现重复订单（另一次运行为 28 个）。前一个线程释放锁时插入尚未提交，下一个线程在 REPEATABLE READ 下读不到它，于是再插入一条；
   - 锁在提交后释放：200 条订单，没有重复；
   - 锁仍在提交前释放，但表上有 `user_id` 唯一键：200 条订单，没有重复，唯一键拒绝了 61 次插入（后一个线程的插入等待前一个事务提交，随后报重复键）。
2. **状态流转用条件更新**（1,000 笔订单，两条路径同时处理每一笔）：
   - 先查后改：支付成功 992 次、关闭成功 998 次，990 笔订单同时有支付时间和关闭时间，最终状态取决于哪个 `UPDATE` 后执行；
   - 条件更新（`WHERE status = 'CREATED'`）：支付 523 次、关闭 477 次，合计正好 1,000，没有订单被两条路径同时改写。
3. **主键类型**（20 万行，3 次中位数）：

| 主键 | 插入耗时 | 数据 | 二级索引 | 合计 |
|---|---:|---:|---:|---:|
| `BIGINT` 自增 | 1,403 ms | 11.5 MB | 15.0 MB | 26.5 MB |
| `BINARY(16)` 有序 UUID | 1,725 ms | 13.5 MB | 18.1 MB | 31.6 MB |
| `CHAR(36)` 随机 UUID | 2,060 ms | 28.6 MB | 30.2 MB | 58.8 MB |

   随机 UUID 比自增慢约 47%，总空间是自增的 2.2 倍：数据页因随机插入频繁分裂、填充率下降；两个二级索引的叶子都带着 36 字节的主键。有序 UUID 只比自增多 19% 空间。

## 五、误差、限制与不能推出的结论

- 重复订单的用户数取决于线程调度，每次运行不同（见过 22、28）；断言只要求提交前释放时大于 0、包住事务时为 0。
- 状态流转用 `CyclicBarrier` 让两条路径同时处理同一笔订单，是最坏情况；真实系统里两条路径撞上的比例取决于回调与关单任务的时间分布，但只要撞上，先查后改就会出错。
- 主键耗时在 2 CPU 的容器、数据全部在 Buffer Pool 里测得；数据量超过内存后随机主键的代价会更大，本实验不测。空间取自 `ANALYZE TABLE` 后的 `information_schema.tables`，是按页统计的估计值。
- 主键断言只检查相对关系：空间 自增 < 有序 UUID < 随机 UUID，随机 UUID 插入慢于自增。

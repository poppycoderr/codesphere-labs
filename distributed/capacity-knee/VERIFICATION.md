# 验证记录：容量拐点

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

1. **吞吐有拐点，拐点之后只是在排队**（MySQL 2 CPU，主键点查）：

| 并发 | QPS | p50 | p99 |
|---:|---:|---:|---:|
| 1 | 14,286 | 0.07 ms | 0.12 ms |
| 4 | 67,650 | 0.06 ms | 0.11 ms |
| 8 | 107,494 | 0.03 ms | 0.09 ms |
| 16 | **107,974** | 0.06 ms | 0.28 ms |
| 32 | 106,842 | 0.12 ms | 0.73 ms |
| 64 | 102,582 | 0.28 ms | 1.50 ms |
| 128 | 94,508 | 0.62 ms | 47.79 ms |
| 256 | 86,773 | 1.43 ms | **57.56 ms** |

   并发 8—16 后吞吐不再增长，再加并发吞吐反而下降，p99 从 0.3 ms 涨到 57 ms。
2. **写入远低于点查**：主键更新（自动提交）最高 11,088 QPS（并发 64），约为点查峰值的十分之一；并发 8 起 p99 就超过 50 ms。
3. **Redis 单实例**：同样 2 CPU，`redis-benchmark` 50 个连接，`GET` 218,914 次/秒，`SET` 197,006 次/秒。

## 二、环境

见 [`evidence/environment.txt`](evidence/environment.txt)。MySQL 8.4.11（2 CPU、1 GB，Buffer Pool 128 MB，关闭 binlog，`innodb_flush_log_at_trx_commit` 为默认的 1），JDK 21 客户端容器不限 CPU，Connector/J 8.0.27（服务端预处理语句）。

## 三、执行步骤

`scripts/verify.sh`：启动共享 MySQL 并建表写入 10 万行，在同一网络的 JDK 21 容器中运行 `src/Capacity.java`（先整体预热 3 秒；每档再预热 3 秒、测 8 秒）；然后启动 Redis 容器，在容器内运行 `redis-benchmark -t set,get -n 500000 -c 50`。

## 四、证据

见 [`evidence/README.md`](evidence/README.md)。文件由 `make evidence` 生成，未手工修改；断言内容见 `scripts/verify.sh`。

## 五、误差、限制与不能推出的结论

- 客户端和 MySQL 在同一台机器上、通过回环地址通信，没有网络往返；客户端也在争用宿主机 CPU。绝对数字只代表这台机器，断言只检查形状：点查的吞吐峰值不在最高并发；最高并发的吞吐不超过峰值的 1.05 倍、p99 是峰值处的 4 倍以上；更新的最高吞吐不到点查峰值的一半；Redis `GET` 高于 MySQL 点查峰值。
- `redis-benchmark` 在 Redis 容器内运行，和服务端共用 2 CPU，没有网络开销。
- 连续两次运行的点查峰值为 110,640 与 107,974 QPS，拐点都在并发 16。

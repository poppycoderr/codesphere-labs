# 验证记录：请求关联：编号、待完成表与迟到的响应

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论与实际结果

| 场景 | 结果 |
|---|---|
| 两个请求共用一个完成对象，B 的响应先到 | A、B 都拿到 B 的结果 |
| 按编号登记独立完成对象，响应乱序 | 各自拿到自己的结果 |
| 先发送后登记，响应在登记前到达 | 调用方一直等待，响应被当作未知编号丢弃，表中残留 1 项 |
| 先登记再发送 | 调用方拿到结果，表中无残留 |
| 1000 个请求超时，超时时不删表项 | 残留 1000 项；删除则为 0 |
| 编号空间为 4，订单 1 超时后编号 0 被订单 5 复用 | 订单 1 的迟到响应完成了订单 5 |
| 编号在连接生命周期内不复用 | 迟到响应作为未知编号丢弃 |
| 连接断开时不通知待完成表 | 在途请求都要等各自超时；全部失败则立即返回「连接已断开」 |
| 写出 Future 成功、对端处理前崩溃 | 业务结果是超时，未知是否执行 |

## 五、误差、限制与不能推出的结论

- 传输层、超时与断连都由脚本驱动，不涉及真实网络与计时器；结论是关于待完成表的状态转换，不测量延迟。
- 「先发送后登记」的竞态在真实网络里取决于响应是否比登记先到，本实验用同进程对端在 send 内同步回复来固定这一交错。

# 验证记录：200 个请求抢 100 个名额：四种聚合写法

> 轻量记录：按 [验证标准](../../docs/verification-standard.md) 的十个部分合并为七节。

## 一、待验证结论

1. 规则写在服务里「先数再插」，三轮都超卖
2. 场次作为聚合根、按版本号乐观更新：不超卖，但热点上大量请求重试 50 次后放弃
3. `SELECT … FOR UPDATE` 锁住聚合根、条件更新 `booked < capacity`：都正好 100 个

## 二、环境

见 [`evidence/environment.txt`](evidence/environment.txt)。组件版本：jdk 21（eclipse-temurin 容器）、mysql 8.4.11、mysql_connector_java 8.0.27。

## 三、执行步骤

`scripts/verify.sh` 依次执行：

1. 启动 MySQL（`shared/docker/mysql84`，项目名 `csl-aggregate`，2 CPU、1 GB）
2. 在共享 MySQL 网络的 JDK 21 容器中运行 `src/Oversell.java`：每种写法 200 个线程、各用一个连接同时发起
3. 用 Python 解析输出并断言

每一项结论都有对应的断言，任何一项不满足即返回非零退出码。

## 五、误差、限制与不能推出的结论

- 超卖数量和乐观锁的成功数每次不同：文章首次实测先数再插 103—122、乐观锁成功 53—55；本仓库归档的一次是 104—114、55—57；另一次复测中有一轮 200 个请求全部「成功」。先数再插的超卖程度取决于并发请求在快照读和插入之间交错得多紧，只能推出「会超卖」，不能推出超卖多少。稳定的结论是四种写法的相对关系。
- 耗时受容器资源限制影响，只用于同一轮内比较。
